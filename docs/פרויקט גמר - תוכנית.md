# פרויקט גמר: METATRON, זרימת גיוס אחת

> מבוסס על הביקורת של יונתן (29.10.2026) ועל דרישות הקורס. קישורים: [[זיכרון פרויקט]] · [[יומן החלטות]]

## ההגדרה (לשליחה ליונתן)
**עברית:**
METATRON: זרימת גיוס אחת מקצה לקצה ב-CrewAI Flow. מוכרים נטענים מקובץ. צוות נתונים מנקה, מנתח ובונה חוזה JSON שמאומת לפני האימון. צוות מודל מאמן ומשווה שני מודלי Lead Scoring שמדרגים את המוכרים.
סוכן מנסח פנייה, המתווך מאשר כל הודעה ב-Streamlit, וההודעה נשלחת בוואטסאפ. התשובה מטופלת, כולל "הסר", ופגישה נקבעת ביומן. בלי שיחה קולית.

**English:**
METATRON: one end-to-end seller-recruitment flow in CrewAI Flow. Sellers are loaded from a file. A data crew cleans the data, runs EDA and writes a JSON data contract that is validated before training. A model crew trains and compares two lead-scoring models that rank the sellers.
An agent drafts the outreach message, the broker approves every message in Streamlit, and it is sent on WhatsApp. The reply is handled, including "remove", and a meeting is booked in the calendar. No voice calls.

## המודל: Lead Scoring
- **מה חוזים:** `agreed_to_meeting`, כלומר האם המוכר יסכים לפגישת גיוס תוך 14 יום מהפנייה. הבעיה בינארית.
- **מאפיינים:**
  - ימים באוויר
  - מספר הורדות מחיר
  - יחס בין המחיר המבוקש לחציון האזור
  - עיר, חדרים, שטח וקומה
  - מספר תמונות ואורך התיאור
  - מקור המודעה
  - האם פורסם בעבר
- **נתונים:** **סינתטיים**, כי עוד אין תוצאות פנייה אמיתיות.
  - מחולל עם seed קבוע (`data/generate.py`), כ-5,000 שורות.
  - פונקציית הסתברות מתועדת עם רעש.
  - **בעיות איכות שהוזרקו בכוונה**, כדי שלצוות הנתונים תהיה עבודה אמיתית: כ-3% כפילויות, ערכים חסרים, חריגים (מחיר פי 10), כתיב לא אחיד של ערים ("ת"א" / "תל אביב") ומספרים ששמורים כטקסט.
- **הסבר בהצגה:** הזרימה עצמה מתעדת תוצאה אמיתית לכל פנייה. לכן גרסה 3 של המודל תאומן על נתונים אמיתיים. זה נכתב גם ב-Model Card.
- **שתי גרסאות:**
  - v1: Logistic Regression כבסיס.
  - v2: Gradient Boosting.
  - **מדדים:** ROC-AUC ו-PR-AUC, ובנוסף **Precision@20%**, כלומר אם המתווך פונה רק ל-20% העליונים, כמה מהם יסכימו לפגישה. לצד זה cross-validation ובדיקת כיול.

## CrewAI Flow
```
TrainingFlow (אופליין)
  ingest_file ──► DataCrew ──► validate_contract ──┬─ failed ──► STOP + דוח שגיאה (אדום ב-Streamlit)
                                                  └─ valid  ──► ModelCrew ──► save model + Model Card

OutreachFlow (לכל מוכר)
  score ──► draft_message ──► await_approval (Streamlit) ──► send (WA / סימולציה)
        ──► handle_reply ──┬─ "הסר"     ──► opt-out גלובלי + אישור הסרה ──► END
                           ├─ לא מעוניין ──► סגירה + תיעוד תוצאה
                           ├─ שאלה      ──► תשובה (עוברת שוב אישור מתווך)
                           └─ מעוניין   ──► propose_slots ──► book_meeting ──► tasks ביומן
  log_outcome ──► תווית לאימון הבא
```

### צוות 1: Data Crew (4 סוכנים)
| סוכן | תפקיד | פלט |
|---|---|---|
| Data Cleaner | כפילויות, ערכים חסרים, טיפוסים ונרמול ערים, דרך כלים דטרמיניסטיים ב-pandas | `clean.parquet` + לוג ניקוי |
| EDA Analyst | התפלגויות, קורלציות והשוואה מול המטרה | `eda/` (גרפים + סטטיסטיקות) |
| Insights Writer | תובנות עסקיות בעברית | `insights.md` |
| Contract Author | חוזה הנתונים | `data_contract.json` |

### שער: אימות החוזה
**נבדק:**
- סכמה וטיפוסים
- טווחים, למשל מחיר חיובי וחדרים בין 1 ל-12
- ערכים מותרים
- `seller_id` ייחודי
- מינימום שורות
- איזון המטרה בטווח סביר

**איך:** pandera או jsonschema. **אם בדיקה נכשלת, ה-Flow נעצר**, נכתב `validation_report.json`, והמסך מציג מה נכשל ואיך מתקנים.

### צוות 2: Model Crew (4 סוכנים)
| סוכן | תפקיד | פלט |
|---|---|---|
| Feature Engineer | מאפיינים וחלוקה ל-train ו-test (stratified, seed) | `features.parquet` |
| Model Trainer | אימון v1 ו-v2 דרך פונקציות קבועות | `models/v1`, `models/v2` |
| Evaluator | מדדים, השוואה ובחירת מודל | `metrics.json` |
| Model Card Writer | Model Card: נתונים, מגבלות, **"סינתטי"** ושימוש הוגן | `MODEL_CARD.md` |

**עיקרון:** הסוכנים מתזמרים, מנתחים וכותבים. **האימון עצמו הוא קוד קבוע** שהם מפעילים ככלי, ולא קוד שה-LLM כותב בכל הרצה.

### שחזור תוצאות
- `config.yaml` אחד
- seed בכל מקום
- hash של קובץ הנתונים נשמר בכל הרצה
- `requirements.lock`
- תיקיית `runs/<run_id>/` לכל הרצה
- פקודה אחת: `python -m metatron.train --config config.yaml`. אותה פקודה על אותם נתונים נותנת אותם מדדים.

## Streamlit: 5 מסכים
1. **נתונים:** ייבוא הקובץ, EDA, התובנות, ומצב חוזה הנתונים (ירוק או אדום).
2. **מודל:** השוואה בין v1 ל-v2 והצגת ה-Model Card.
3. **תור אישור:** המוכרים מדורגים לפי ציון. ליד כל אחד ההודעה שנוסחה, עם הכפתורים **אשר / ערוך / דחה**.
4. **שיחות:** הצגת השיחה בוואטסאפ או בסימולטור, ו**רשימת ה"הסר"**.
5. **יומן:** הפגישות שנקבעו.

## וואטסאפ
- **שליחה אמיתית:** דרך Cloud API, **רק למספרים שלכם** בזמן הפיתוח וההדגמה.
- **גיבוי:** מצב סימולציה, אם תבנית ההודעה עוד לא אושרה.
- **"הסר":**
  - מזוהה גם בניסוחים חופשיים ("תורידו אותי", "לא להתקשר").
  - נכנס לרשימת opt-out גלובלית.
  - נשלחת הודעת אישור אחת.
  - כל שליחה עתידית לאותו מספר נחסמת. יש לזה גם טסט.

## תסריט הדגמה (כ-5 דקות)
1. מעלים קובץ "מלוכלך". צוות הנתונים מנקה, והחוזה ירוק.
2. **מעלים קובץ שבור, וה-Flow נעצר עם הסבר.**
3. השוואת המודלים ו-Model Card.
4. תור אישור: **המתווך עורך ומאשר** את המוכר בעל הציון הגבוה.
5. ההודעה מגיעה לטלפון. עונים "מעוניין", בוחרים מועד, והפגישה מופיעה ביומן.
6. מוכר שני עונה **"הסר"**. מקבל הודעת אישור, וניסיון שליחה נוסף נחסם.
